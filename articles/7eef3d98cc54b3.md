## はじめに
はじめまして。つぼこです！
初記事作成ということで、なんとなく理解していた「インデックス」についてまとめてみました。
「詳しくは分からないけど、インデックスは張った方がいいんでしょ？」と考えている方の参考になれば幸いです！

## 「インデックス」とは？
「インデックス」は、日本語で「索引」「見出し」などと訳されます。
つまり、「インデックス」を張る = 「**索引を作る**」ということです。
分厚い辞書から一つの単語を見つけ出す時、1ページずつ捲って探していくのは大変なので、
索引を見て目的のページを開くと思います。
簡単に言えば、それと同じことをDBでもやってあげよう、ということなのです。

## なぜ速くなる？「B+Tree構造」の仕組み
ではなぜ「索引を作る」と速くなるのでしょうか。
その秘密は、「**目的のデータにたどり着くための方法**」にあります。

### インデックスを張らなかった場合
インデックスを張らなかった場合、一つのデータを探すにはDBの中にあるデータを一件ずつ見ていくことになります。
この探し方を「線形探索(せんけいたんさく)」と言います。
計算量は、`O(n)`と表されます。
:::message
プログラムの計算量を表すには「O記法」を用います。Oはorderで計算量のこと。
nにはデータ数が入ります。
:::

usersテーブルから名前が runa のデータを探したい時を考えます。
```sql
SELECT * FROM users WHERE name = 'runa';
```
![線形探索のイメージ](/images/1.png)

インデックスを張っていない場合、上から runa を探すため、7回データを読むことになります。
:::message alert
もしも100万件のデータがあり、その最後に目的のデータがあるのなら、
100万件を読むことに...！
:::

### インデックスを張った場合
インデックスを張った場合、検索専用の索引データが裏側で生成されます。
そのDBの構造こそ、「**B+Tree構造**」と呼ばれるものです。
「B+Tree構造」は少々複雑なため、まず「B-Tree構造」について説明します。

「B-Tree構造」は、ルートノード、内部ノード、リーフノードからなるものです。
![B-Treeのイメージ](/images/5.png)
一つのノードには、キーとポインタの組み合わせが入ります。
| 要素 | 中身 |
| ---- | ---- |
| キー | CREATE INDEX で指定したカラムのデータ |
| ポインタ | 次のノードへの案内情報<br>本物のレコードを特定する情報 |

計算量は、`O(log n)`と表されます。

先ほどと同じく、usersテーブルから名前が runa のデータを探したい時を考えます。
```sql
SELECT * FROM users WHERE name = 'runa';
```
インデックスを name カラムに張ります。
```sql
CREATE INDEX idx_users_name ON users(name);
```
そうすると、次のような検索用の「B-Tree構造」が作成されます。

![B-Treeのイメージ](/images/2.png)

※今回の場合キーである数字はアルファベット順に振られています。
1. 4(riho)と5(runa)を比べると5の方が大きい → 右に進む
2. 5(runa)と6(shun)を比べると6の方が大きい → 左に進む
3. 5(runa)を発見！ 

:::message
**分岐していくことで探索の回数を大幅に減らすことができる**のです。
:::

#### 実務で使われる「B+Tree」とは？
MySQLなどの多くのデータベースでは、「B-Tree構造」をさらに進化させた「B+Tree構造」が採用されています。
「B-Tree構造」との主な違いは、以下です。
- 本物のレコードを特定する情報は、すべて一番下のリーフノードに集約する
- リーフノード同士が順番につながっているため、範囲検索や並び順の取得が効率的
例：`SELECT * FROM users WHERE created_at >= '2026-08-01';`

![B+Treeのイメージ](/images/3.png)

また、**ルートノード、中間ノードを案内役に特化させる**ことにより、次で説明するような凄まじい検索スピードを実現しています。

### 「B+Tree構造」なら検索回数は最大3回?
「B+Tree構造」でよく言われているのが、**最大3〜4回のノード確認でデータに辿り着ける**ということ。
...なんで？100万件とかあったら、何十階層も必要になるんじゃないの...？と疑問に思うかもしれません。

そうならない理由は、**1つのノードに詰め込める、キーとポインタの数が多いから**です。

MySQLの1ノードは16KBの容量を持っています。
ここで、キーとなるデータとポインタのサイズを以下のように仮定してみます。
- **キーのデータ（BIGINT型）:** 8バイト
- **ポインタ（一般的な64bitのアドレス）:** 8バイト

この場合、一つのキーとポインタの組み合わせに必要なのは、`8バイト + 8バイト = 16バイト` となります。

16KB = 16,384バイトなので、`16,384バイト ÷ 16バイト = 1,024`
つまり、**1つのノードに1,024個の組み合わせが入ります**。

組み合わせの数を約1,000として計算すると、階層ごとのデータ件数は以下になります。
※ 厳密には、分岐数 = 組み合わせの数＋1 なので1,025分岐ですが、
ここでは分かりやすく分岐数も「約1,000分岐」として計算しています。

| 階層 | 計算式 | データ件数 |
| ---- | ---- | ---- |
| 1階層 | 1,000 | 1,000件 |
| 2階層 | 1,000 × 1,000 | 100万件 |
| 3階層 | 1,000 × 1,000 × 1,000 | 10億件 |

このように1階層深くなるとデータ容量が1,000倍になります。
:::message
100万件〜10億件のデータでも、**たった3回**のアクセスで目的のデータに辿り着くことができるのです。
:::

## 【ハンズオン】インデックスを張ることの効果を測定！
実際に、100万件のデータを用意し、インデックスを張ることによってどのくらい速くなるのか実験をします。
今回は、MySQLを使用しました。

### インデックスなしのパターン
まず、インデックスなしのパターンを検証します。
```
mysql> SELECT * FROM users WHERE name = 'runa';
+---------+------+--------+----------------------------+----------------------------+
| id      | name | gender | created_at                 | updated_at                 |
+---------+------+--------+----------------------------+----------------------------+
| 1000000 | runa | woman  | 2026-08-15 04:23:46.705103 | 2026-08-15 04:23:46.705103 |
+---------+------+--------+----------------------------+----------------------------+
1 row in set (0.209 sec)
```
usersテーブルから、name が runa のレコードを探してもらうと、**0.209秒**かかったことが分かりました。
SQL文の冒頭にEXPLAINをつけて、どのようにスキャンしたかと確認行数を見ます。
```
mysql> EXPLAIN SELECT * FROM users WHERE name = 'runa';
+---------------------------------------------------------------------------------------------------------------------+
| EXPLAIN                                                                                                             |
+---------------------------------------------------------------------------------------------------------------------+
| -> Filter: (users.`name` = 'runa')  (cost=100594 rows=99640)
    -> Table scan on users  (cost=100594 rows=996401)
 |
+---------------------------------------------------------------------------------------------------------------------+
1 row in set (0.002 sec)
```
全てのレコードをスキャンし、**約100万行**を確認していることが分かります。

### インデックスありのパターン
次にインデックスありのパターンを検証します。
初めに、インデックスを作成します。
今回は、nameカラムにインデックスを作成しました。
```
mysql> CREATE INDEX idx_users_name ON users(name);
```
```
mysql> SELECT * FROM users WHERE name = 'runa';
+---------+------+--------+----------------------------+----------------------------+
| id      | name | gender | created_at                 | updated_at                 |
+---------+------+--------+----------------------------+----------------------------+
| 1000000 | runa | woman  | 2026-08-15 04:23:46.705103 | 2026-08-15 04:23:46.705103 |
+---------+------+--------+----------------------------+----------------------------+
1 row in set (0.002 sec)
```
usersテーブルから、name が runa のレコードを探してもらうと、**0.002秒**かかったことが分かりました。
SQL文の冒頭にEXPLAINをつけて、どのようにスキャンしたかと確認行数を見ます。
```
mysql> EXPLAIN SELECT * FROM users WHERE name = 'runa';
+------------------------------------------------------------------------------------+
| EXPLAIN                                                                            |
+------------------------------------------------------------------------------------+
| -> Index lookup on users using idx_users_name (name = 'runa')  (cost=0.35 rows=1)
 |
+------------------------------------------------------------------------------------+
1 row in set (0.001 sec)
```
インデックスを使用し、**1行のみ**確認していることが分かります。

### 実験結果：インデックスを張ると約100倍高速に！
実験結果をまとめると次のようになります。

| 項目 | インデックスなし | インデックスあり |
| ---- | ---- | ---- |
| 実行時間 | 0.209 sec | 0.002 sec |
| スキャン方法 | Table scan on users | Index lookup using idx_users_name |
| チェック行数 | 996,401行 | 1行 |

インデックスを張ることで、**実行時間が約100倍高速**になりました！
また、チェック行数は、インデックスを張ることで、**たったの1行**となっています。

これは、先ほどのB+Tree構造で目当てのデータを見つけ出し、
ポインタを使ってテーブル本体の行を1件だけ直接読み込んだためです。

今回は簡単なテーブル構造のため、インデックスを張らなくても約0.2秒で目当てのデータを取得できました。
しかし、カラム数が増えたり、テーブルが結合されたりすると、インデックスなしでの取得時間は長くなっていきます。
:::message alert
データが小さいうちは気づきにくいですが、データが増えたり要件が複雑になったりしたときに必須の仕組みが、インデックスなのです。
:::

## 【要注意】インデックスを張りすぎるとダメな理由
「それじゃあ、インデックスを全部のカラムに張っておけばいいんだ！」と思っている人、
それは危険です！

インデックスを張りすぎると、以下の問題が発生する恐れがあります。
① ストレージの肥大化
② オプティマイザーの誤作動(誤ったインデックスの利用)

### ① ストレージの肥大化
インデックスを張る際、テーブル本体とは別に「検索用の独立したデータ構造（MySQLの場合はB+Tree）」をストレージ上に保持します。

不要なカラムにまでインデックスを作成すると、
**テーブル本体のデータサイズ以上にインデックス全体のデータサイズが肥大化**して、
ストレージの容量を圧迫してしまいます。

また、DBは高速化のために、データやインデックスをメモリにキャッシュします。
インデックスの量が大きくなりすぎるとメモリに収まりきらなくなり、**本来メモリに置いて頻繁に参照したいデータがメモリから追い出されてしまう**可能性があります。

:::message alert
「データ量は数GBなのに、インデックスだけで数十GB」という状態になると、
サーバー代やディスク代だけでなく、データベース全体の応答性にも深刻な影響を与えます。
:::

### ② オプティマイザーの誤作動(誤ったインデックスの利用)
DBにはSQLを受け取った際に、処理時間や負荷が少なくて済むデータの取得方法を瞬時に選んでくれる、**オプティマイザー**という機能が備わっています。
不要なインデックスが大量に存在すると、オプティマイザーの計算が複雑になってしまい、本来使うべきインデックスではなく、効率の悪いインデックスが誤って選ばれるリスクがあります。

:::message alert
最適ではないインデックスが選択された場合、フルスキャンよりも実行時間が延びてしまう可能性もあります。
:::

## どんな時にインデックスを張るべきか
では、どんな時にインデックスを張るべきなのでしょう。
以下の**3つ**の基準を是非参考にしてみてください！

### ① カーディナリティが高いカラムか？
かーでぃなりてぃ...？

カーディナリティとは、値の種類のことです。
- カーディナリティが高いもの
`name`, `user_id`, `created_at` など、値がバラバラで一意に近いもの
→ **1〜数件に一気に絞り込める**ため効果が高い
- カーディナリティが低いもの
`gender` や `is_deleted`（true/false) など
→ **絞り込みができない**ため、オプティマイザーに無視されてフルスキャンされがち
:::message
ハンズオンで使った `EXPLAIN` は、オプティマイザーが決めたデータの取得方法を
表示するコマンドとなっています。
:::

なお、基本的にカーディナリティが高いものを選ぶと良いですが、条件に一致する行が多ければ**結果的にフルスキャンになる場合もあります**。
逆にカーディナリティが低くても、集計や期間指定などで**頻繁に使う場合は選択した方が良いケース**もあります。
実際の利用状況を見て判断するようにしましょう！

### ② WHERE / JOIN / ORDER BY で頻繁に使われるか？
- `WHERE user_id = ?`（検索条件）
- `users.id = orders.user_id`（テーブル結合のキー）
-  `ORDER BY created_at DESC`（並び替え）

**日常的に大量に叩かれるクエリの対象カラム**がインデックスの候補になります。

### ③ テーブルのデータ件数が十分に多いか？
数百件〜数千件程度の小さなテーブルであれば、インデックスを張るよりも
最初からフルスキャンした方が速いケースもあります。
**肥大化していくテーブル**に、インデックスは張ってあげましょう。
