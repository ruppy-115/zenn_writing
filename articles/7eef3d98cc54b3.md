## はじめに
はじめまして。つぼこです！
初記事作成ということで、なんとなく理解していた「インデックス」についてまとめてみました。
「詳しくは分からないけど、インデックスは貼った方がいいんでしょ？」と考えている方の参考になれば幸いです！

## 「インデックス」とは？
「インデックス」は、日本語で「索引」「見出し」などと訳されます。
つまり、「インデックス」を貼る = 「索引を作る」ということです。
分厚い辞書から一つの単語を見つけ出す時、1ページずつ捲って探していくのは大変なので、索引を見て目的のページを開くと思います。
簡単に言えば、それと同じことをDBでもやってあげよう、ということなのです。

## なぜ速くなる？「B+Tree構造」の仕組み
ではなぜ「索引を作る」と速くなるのでしょうか。
その秘密は、「目的のデータにたどり着くための方法」にあります。

### インデックスを貼らなかった場合
インデックスを貼らなかった場合、一つのデータを探すにはDBの中にあるデータを一件ずつ見ていくことになります。
この探し方を「線形探索(せんけいたんさく)」と言います。
計算量は、O(n)と表されます。
（プログラムの計算量を表すには「O記法」を用います。Oはorderで計算量のこと。nにはデータ数が入ります。）

ユーザーテーブルから名前が runa のデータを探したい時を考えます。
```
SELECT * FROM user WHERE name = "runa"
```
![線形探索のイメージ](/images/1.png)

インデックスを貼っていない場合、上から、runa を探すため、7回データを読むことになります。
そのため、もしも100万件のデータがあり、その最後に目的のデータがあるのなら、100万件を読むことに...！

### インデックスを貼った場合
インデックスを貼った場合、検索専用の索引データが裏側で生成されます。
そのDBの構造こそ、「B+Tree構造」と呼ばれるものです。
「B+Tree構造」は少し複雑なため、まず「B-Tree構造」について説明します。

「B-Tree構造」は、ルートノード、内部ノード、リーフノードからなるものです。
一つのノードには、キーとポインタの組み合わせが入ります。
| 要素 | 決める人 | 中身
| ---- | ---- | ----
| キー | エンジニア | CREATE INDEX で指定したカラムのデータ
| ポインタ | DBシステム(自動) | 本物のデータの位置(MySQLの場合は主キー)

計算量は、O(log n)と表されます。

先ほどと同じく、ユーザーテーブルから名前が runa のデータを探したい時を考えます。
```
SELECT * FROM user WHERE name = "runa"
```
まず、インデックスを name カラムに貼ります。
```
CREATE INDEX idx_user_name ON user(name);
```
そうすると、次のような検索用のデータベースが作成されます。

![B-Treeのイメージ](/images/2.png)

分岐していくことで探索の回数を大幅に減らすことができるのです。

#### 実務で使われる「B+Tree」とは？
MySQLなどの多くのデータベースでは、「B-Tree構造」をさらに進化させた「B+Tree構造」が採用されています。
「B-Tree構造」との一番の違いは、以下です。
- ルートノードや中間ノードには案内情報（キーと子ノードへのポインタ）だけを置く
- 実データはすべて一番下のリーフノードに集約する

![B+Treeのイメージ](/images/3.png)

中間ノードを案内役に特化させることで、次で説明するような凄まじい探索スピードを実現しています。

### 「B+Tree構造」なら検索回数は最大3回?
「B+Tree構造」でよく言われているのが、最大3〜4回のノード確認でデータに辿り着けるということ。
...なんで？100万件とかあったら、何十階層も必要になるんじゃないの...？と疑問に思うかもしれません。

そうならない理由は、1つのノードに詰め込める、キーとポインタの数が多いからです。
例えば、MySQLの1ノードは16KBの容量を持っています。
BIGINT型のデータは8バイト、子ノードへのポインタ6バイトとすると、一つのキーとポインタの組み合わせに必要なのは、14バイト。
16KB = 16,384バイトなので、16,384バイト ÷ 14バイト = 1,170
つまり、一つのノードに約1,000個の組み合わせ(分岐)が入ります。
この分岐の数を1,000として計算すると、階層ごとのデータ件数は以下になります。

| 階層 | 計算式 | データ件数
| ---- | ---- | ----
| 1階層 | 1,000 | 1000件
| 2階層 | 1,000 × 1,000 | 100万件
| 3階層 | 1,000 × 1,000 × 1,000 | 10億件

このように1階層深くなるとデータ容量が1,000倍になります。
100万件〜10億件のデータでも3回のアクセスで目的のデータに辿り着くことができるのです。

## 【ハンズオン】インデックスを貼ることの効果を測定！
実際に、100万件のデータを用意し、インデックスを貼ることによってどのくらい速くなるのか実験をします。
今回は、MySQLを使用しました。

### インデックスなしのパターン
まず、インデックスなしのパターンを検証します。
```
mysql> SELECT * FROM users WHERE name = 'runa';
+---------+------+--------+----------------------------+----------------------------+
| id      | name | gender | created_at                 | updated_at                 |
+---------+------+--------+----------------------------+----------------------------+
| 1000000 | runa | woman  | 2026-08-15 04:23:46.705103 | 2026-08-15 04:23:46.705103 |
+---------+------+--------+----------------------------+----------------------------+
1 row in set (0.209 sec)
```
Usersテーブルから、name が runa のレコードを探してもらうと、0.209秒かかったことが分かりました。
SQL文の冒頭にEXPLAINをつけて、どのようにスキャンしたかと確認行数を見ます。
```
mysql> EXPLAIN SELECT * FROM users WHERE name = 'runa';
+---------------------------------------------------------------------------------------------------------------------+
| EXPLAIN                                                                                                             |
+---------------------------------------------------------------------------------------------------------------------+
| -> Filter: (users.`name` = 'runa')  (cost=100594 rows=99640)
    -> Table scan on users  (cost=100594 rows=996401)
 |
+---------------------------------------------------------------------------------------------------------------------+
1 row in set (0.002 sec)
```
全てのテーブルをスキャンし、約100万行を確認していることが分かります。

### インデックスありのパターン
次にインデックスありのパターンを検証します。
初めに、インデックスを作成します。
今回は、nameカラムにインデックスを作成しました。
```
mysql> CREATE INDEX idx_users_name ON users(name);
```
```
mysql> SELECT * FROM users WHERE name = 'runa';
+---------+------+--------+----------------------------+----------------------------+
| id      | name | gender | created_at                 | updated_at                 |
+---------+------+--------+----------------------------+----------------------------+
| 1000000 | runa | woman  | 2026-08-15 04:23:46.705103 | 2026-08-15 04:23:46.705103 |
+---------+------+--------+----------------------------+----------------------------+
1 row in set (0.002 sec)
```
Usersテーブルから、name が runa のレコードを探してもらうと、0.002秒かかったことが分かりました。
SQL文の冒頭にEXPLAINをつけて、どのようにスキャンしたかと確認行数を見ます。
```
mysql> EXPLAIN SELECT * FROM users WHERE name = 'runa';
+------------------------------------------------------------------------------------+
| EXPLAIN                                                                            |
+------------------------------------------------------------------------------------+
| -> Index lookup on users using idx_users_name (name = 'runa')  (cost=0.35 rows=1)
 |
+------------------------------------------------------------------------------------+
1 row in set (0.001 sec)
```
インデックスを使用し、1行のみ確認していることが分かります。

### 実験結果：インデックスを貼ると約100倍高速に！
実験結果をまとめると次のようになります。

|  | インデックスなし | インデックスあり
| ---- | ---- | ----
| 実行時間 | 0.209 sec | 0.002 sec
| スキャン方法 | Table scan on users | Index lookup using idx_users_name
| チェック行数 | 996,401行 | 1行

インデックスを貼ることで、実行時間が約100倍高速になりました！
また、チェック行数は、インデックスを貼ることで、たったの1行となっています。
これは、先ほどのB+Tree構造で目当てのデータを見つけ出し、ポインタを使ってテーブル本体の行を1件だけ直接読み込んだためです。

今回は簡単なテーブル構造のため、インデックスを貼らなくても約0.2秒で目当てのデータを取得できました。
しかし、カラム数が増えたり、テーブルが結合されたりすると、インデックスなしでの取得時間は長くなっていきます。
データが小さいうちは気づきにくいですが、データが増えたり要件が複雑になったりしたときに必須の仕組みが、インデックスなのです。

## 【要注意】インデックスを貼りすぎるとダメな理由
「それじゃあ、インデックスを全部のカラムに貼っておけばいいんだ！」と思っている人、いるのではないでしょうか？
実は、貼りすぎるとDBへの書き込み(INSERT / UPDATE / DELETE)が遅くなってしまうのです。

その原因が、「B-Tree構造」特有の「ノードの再構成」です。

### データの追加で何が起こる？ 
先ほども述べたように、1つのノードに入れられる容量は決まっています。
もし満杯のノードに新しいデータが追加されると、以下のような再構成が始まります。

1. データを追加しようとしても容量が足りない
2. 並べた時の真ん中のデータを親ノードへ
3. ノードを2つに分裂させて左右に振り分ける

例：ノードに入れられる組み合わせが2つまでの場合
![再構成](/images/4.png)


そのため、インデックスを貼りすぎると、再構成の動作が頻発し、重たくなってしまうのです。
インデックスは検索を早くする画期的なシステムですが、むやみに貼るのはよくないのですね...。

## どんな時にインデックスを貼るべきか
では、どんな時にインデックスを貼るべきなのでしょう。
以下の3つの基準を是非参考にしてみてください！

### ① カーディナリティが高いカラムか？
かーでぃなりてぃ...？

カーディナリティとは、値の種類のことです。
- カーディナリティが高いもの
`name`, `user_id`, `created_at` など、値がバラバラで一意に近いもの
→ **1〜数件に一気に絞り込める**ため効果が高い！
- カーディナリティが低いもの
`gender` や `is_deleted`（true/false) など
→ 絞り込みができないため、オプティマイザに無視されてフルスキャンされがち

### ② WHERE / JOIN / ORDER BY で頻繁に使われるか？
- `WHERE user_id = ?`（検索条件）
- `users.id = orders.user_id`（テーブル結合のキー）
-  `ORDER BY created_at DESC`（並び替え）
**日常的に大量に叩かれるクエリの対象カラム**がインデックスの候補になります

### ③ テーブルのデータ件数が十分に多いか？
数百件〜数千件程度の小さなテーブルであれば、インデックスを引くオーバーヘッドよりも、最初からフルスキャンした方が速いケースもあります。
**肥大化していくテーブル**に、インデックスは貼ってあげましょう。
