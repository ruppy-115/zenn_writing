## はじめに
お疲れ様です！坪子です！
テーブルにカラムを追加する際、テーブルロックについて事前に調べる必要がありますが、
恥ずかしながら、その理由や仕組みについてよく知らなかったため、今回調べてみることにしました。
「実際の調査ではどこを見たらいいのか」や「万が一テーブルロックで処理が詰まってしまった時の対処法」も一緒にまとめるので、是非ご覧ください！

## カラム追加の際のテーブルロックとは
データベースには、データの整合性を保つために「ロック」という仕組みがあります。
ロックにより、ある処理がデータを更新している間に別の処理から書き換えられ、
データの矛盾が起きてしまうことを防いでいます。

MySQLにおけるロックは、内部構造に合わせておおまかに
「**InnoDBロック**」と「**メタデータロック**」の2つに分かれています。

- InnoDBロック：主に「行（レコード）」単位でデータそのものを守る
- メタデータロック：テーブルの「構造（定義・設計図）」を守る

今回扱う「カラム追加時のテーブルロック」の正体は...後者の**メタデータロック**です！
テーブルの構造そのものを守るため、対象テーブル全体に対してアクセス制限（ロック）をかけます。

:::details 【重要】メタデータロックの「共有ロック」と「排他ロック」
メタデータロック（MDL）には、大きく分けて2つのモードがあります。

- **共有ロック（Shared MDL）**  
  「テーブル定義が変わらないこと」を保証するロック。通常の `SELECT`, `INSERT`, `UPDATE` などが自動で取得します。**共有ロック同士はお互いを邪魔しない**ため、普段何百人ものユーザーが同時に読み書きしても処理が詰まることはありません。
- **排他ロック（Exclusive MDL）**  
  「テーブル定義を変更する」ための強力なロック。カラム追加（`ALTER TABLE`）などのDDLが取得します。**排他ロックは他のすべてのロック（共有・排他問わず）と衝突する**ため、誰かがテーブルを触っている間は取得できません。
:::

## カラム追加の際にテーブルロックについて調査する理由
ではなぜカラム追加の際に、テーブルロックについて調査する必要があるのでしょうか。
その理由は、**たった1つのカラム追加で、サービス全体が停止する可能性がある**からです。

以降では、データベースで起きていることと、それにより引き起こされる大惨事について説明します！

### データベースの裏側で何が起きている？
トランザクション内で参照や更新を行っているテーブルに対して、途中でDDL（テーブル構造を変更する操作）が割り込んでしまうと、データの整合性が失われてしまいます。

<図>

そのためMySQLは、整合性を保つために以下のような制御を行います。

1. **先行トランザクションがメタデータロックを取得**  
   あるトランザクションがテーブルにアクセス（参照や更新）すると、その間にテーブル定義が変わらないよう、先程説明した「メタデータロック」を取得します。
<図>
2. **DDLが待機状態になる**  
   そのトランザクションが実行されている間にカラム追加（`ALTER TABLE`）を実行すると、排他的なロックが取れずに**待機状態**になります。
<図>
3. **先行トランザクションが終了すると解放**  
   先行するトランザクションが完了（COMMIT や ROLLBACK）して、メタデータロックが解放されるまで、DDLはずっと待たされ続けます。
<図>

ここまでは、データの整合性を守るための正常な動作と言えますね。
しかし、問題はこの後です...。

### 大惨事になりうる理由
「DDLが裏で待たされるだけなら、数秒〜数十秒待てばいいのでは？」と、思うかもしれませんが、それは危険です...！

MySQLには、「**排他ロック（DDL）が待機列の先頭にいる間は、後から来た共有ロック（通常のSELECTやINSERT）も通してはいけない**」というルールがあります。
後続クエリを優先し続けると、DDLが永遠に実行できないためです。

その結果、「**DDLが待機列の先頭に並ぶと、後から来た通常のクエリ（SELECTやINSERTなど）もすべてその後ろに並ばされて待機状態になる**」という事故が発生します。

<図>
```text
[先行の長い処理] ─── MDLを握りっぱなし
       │
       ▼
[カラム追加 DDL] ─── 「終わるまで待機...」
       │
       ▼
[後続のWebリクエスト] ── SELECT / INSERT もすべてDDLの後ろでストップ！
[後続のWebリクエスト] ── 待機...
[後続のWebリクエスト] ── 待機...（コネクション枯渇・サービス停止）
```

DDLが足止めされている間、ユーザーの通常アクセス（SELECTやINSERT）も同じく足止めされます。
足止めだけでなく、DB接続数の上限（`Too many connections`）に達し、サービス全体が500エラーや画面フリーズでダウンしてしまうことも考えられます。

### MySQLのオンラインDDLならロックはかからない？
ここでひとつの疑問が浮かぶかもしれません。  
「**MySQLにはオンラインDDLがあるから、DDLの間も読み書きできる（ロックされない）はずでは？**」

オンラインDDLとは、**サービスを稼働させたまま（オンラインのまま）、裏でテーブルの構造変更を行うための仕組み**です。
MySQLのバージョンアップに伴い、DDLの裏側の仕組み（アルゴリズム）は大きく3世代に進化してきました。

#### オンラインDDLの3つのアルゴリズムと仕組み
1. **`COPY`**（MySQL 5.5以前）
   * **仕組み：** 変更後の構造を持つ「新しい一時テーブル」を裏で作成し、元テーブルの全データを1行ずつコピーして差し替えます。
   * **ロック：** コピー作業中はずっと共有ロックがかかり、**テーブルへの書き込み（INSERT/UPDATE/DELETE）が遮断**されます。
<図>
2. **`INPLACE`**（MySQL 5.6以降）
   * **仕組み：** テーブルの丸ごとコピーを原則行わず、既存のテーブルスペース内で構造変更を行います。作業中に発生した書き込みデータは「一時ログ（Online DDL Log）」に記録しておき、変更完了時に一気に反映します。
   * **ロック：** 作業中も**読み取り・書き込みの両方が可能**になりました。
<図>
3. **`INSTANT`**（MySQL 8.0以降）
   * **仕組み：** 実データ（レコード）には一切手を加えず、MySQLのデータ辞書にある**「テーブルのメタデータ（定義情報）」だけを書き換えます**。既存のデータ行はそのまま残し、読み書き時に新しい定義を適用します。
   * **ロック：** データ件数が数千万件あっても、処理時間は**データ量に依存せず文字通り「一瞬（ミリ秒単位）」**で完了します。
<図>

#### オンラインDDLでも事前調査が必要な理由
安全にDDLができるのなら調査する必要はないのでは？とつい考えてしまいますが、
事前調査が必須とされる理由は主に2つあります！

1. **開始時に、メタデータロックを取得するから**  
   `INPLACE`や`INSTANT`であっても、処理の実行には排他的なメタデータロックの取得が不可欠です。 
   そのため、**処理の開始時にたった1つでも重い先行クエリがいれば、待機列が発生し、後続クエリを巻き込んで大渋滞が起きます**。
<図>
2. **すべてのカラム追加が`INSTANT`で動くわけではないから**  
   MySQL 8.0だからといって、**どんなカラム追加にも`INSTANT`が使われるわけではありません**。  
   追加する位置（MySQLのマイナーバージョンによる制限）や、データ型、制約、テーブルのオプションによっては、`INSTANT`が使えず、`INPLACE`や`COPY`が使われます。

「オンラインDDLがあるから大丈夫だろう」と過信せず、今回追加するカラムは**どのアルゴリズム（INSTANT / INPLACE / COPY）で動き**、**どんなロックを取得するのか**を事前に把握しておくことが不可欠なのです。

## 【ハンズオン】手元で動かしてロックの挙動を検証してみよう！
理屈が分かったところで、ここからは手元のPCで実際にMySQLを動かしながら、以下を試してみましょう！

- **影響範囲を確認する**
- **`ALTER TABLE`が`INSTANT`で動くか検証**
- **わざとロックを発生させて`SHOW PROCESSLIST`で監視する**

### 事前準備
手軽に試せるよう、Dockerを使い、MySQL 8.0の環境を用意します。  

ターミナルを開き、以下のコマンドでMySQLコンテナを起動します。
```bash
docker run -d --name mysql-lock-test -e MYSQL_ROOT_PASSWORD=password -p 3306:3306 mysql:8.0
```

起動したら、MySQLに入って検証用のデータベースとテーブルを作成します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword
```

```sql
-- 検証用データベース作成
CREATE DATABASE lock_test;
USE lock_test;

-- 検証用テーブル作成
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- ダミーデータを投入（数件）
INSERT INTO users (name, email) VALUES 
('Alice', 'alice@example.com'),
('Bob', 'bob@example.com'),
('Charlie', 'charlie@example.com');
```

これで準備完了です！

### 影響範囲の確認
まずは、対象テーブルの行数やデータサイズを調べてみましょう。
万が一、`INPLACE`や`COPY`が動いた場合、処理時間や負荷はデータ量に直結します。

```sql
SELECT 
    table_name,
    table_rows AS approx_rows,
    ROUND(data_length / 1024 / 1024, 2) AS data_size_mb,
    ROUND(index_length / 1024 / 1024, 2) AS index_size_mb
FROM 
    information_schema.tables
WHERE 
    table_schema = DATABASE()
    AND table_name = 'users';
```

#### 出力結果の例
```text
+------------+-------------+--------------+---------------+
| TABLE_NAME | approx_rows | data_size_mb | index_size_mb |
+------------+-------------+--------------+---------------+
| users      |           3 |         0.02 |          0.00 |
+------------+-------------+--------------+---------------+
```
本番環境で、「数百万行」「数GB」になっている場合は、再構築（Rebuild）が走った際のリスクが高いため、特に慎重なテストが必要です。

### `ALTER TABLE`が`INSTANT`で動くかの検証
続いて、追加したいカラムが`INSTANT`で通るかをテストします。
ポイントは、**オプションを指定すること**です。

```sql
-- INSTANT を指定してカラム追加を試す
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INSTANT;
```

**実行結果：**
```text
Query OK, 0 rows affected (0.03 sec)
Records: 0  Duplicates: 0  Warnings: 0
```
このように `0.03 sec` などミリ秒単位で成功すれば、MySQL 8.0の`INSTANT`が有効に働いています。
実データへの再構築は走っておらず、安全に追加できることが確認できます。

### わざとロックを発生させ,`SHOW PROCESSLIST`で監視
記事の前半で解説した、
「**先行トランザクションによってDDLが詰まり、後続のSELECTまで巻き込まれる現象**」を、
実際に手元で再現してみましょう！

ターミナルを **4つ** 開いて実験します。

```text
[ターミナル1] 先行クエリ
[ターミナル2] カラム追加
[ターミナル3] 後続のクエリ
[ターミナル4] 監視
```

#### 手順1：【ターミナル1】トランザクションを開いて放置する
まずは先行トランザクションを作り、テーブルの「共有メタデータロック」を握ったままにします。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
START TRANSACTION;
SELECT * FROM users WHERE id = 1;
-- ※ COMMIT も ROLLBACK も打たずにこのまま放置します！
```

#### 手順2：【ターミナル2】カラム追加（`ALTER TABLE`）を実行する
2つ目のターミナルを開き、カラム追加を実行してみます。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
ALTER TABLE users ADD COLUMN age INT;
```
**プロンプトが返ってこず、画面が止まります！**  
ターミナル1が共有メタデータロックを握っているため、排他メタデータロックが取れず、
DDLが待機列に並んだ状態です。

#### 手順3：【ターミナル3】後続のクエリを実行する
3つ目のターミナルを開き、ユーザーのアクセスを想定した通常の`SELECT`を実行します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
SELECT * FROM users;
```
**ただの`SELECT`ですが、画面が止まります！**  
待機列の先頭に`ALTER TABLE`がいるため、足止めされてしまいました。

#### 手順4：【ターミナル4】プロセスの状態を監視する
4つ目のターミナルを開き、何が起きているかを確認します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
SHOW FULL PROCESSLIST;
```

##### 出力結果
```text
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
| Id | User | Host      | db        | Command | Time | State                           | Info                                 |
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
|  8 | root | localhost | lock_test | Sleep   |   95 |                                 | NULL                                 |
|  9 | root | localhost | lock_test | Query   |   76 | Waiting for table metadata lock | ALTER TABLE users ADD COLUMN age INT |
| 10 | root | localhost | lock_test | Query   |   21 | Waiting for table metadata lock | SELECT * FROM users                  |
| 11 | root | localhost | lock_test | Query   |    0 | init                            | SHOW FULL PROCESSLIST                |
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
```

- **Id: 9** の`ALTER TABLE`が`Waiting for table metadata lock`になっています。
- **Id: 8** は`Command: Sleep`（クエリ自体は終わっている）ですが、95秒間トランザクションを開いたまま放置しているため、これが原因だと突き止められます。

#### 手順5：【ターミナル1】を解放
ターミナル1に戻って、`COMMIT;`または`ROLLBACK;`を打つと、ターミナル2の`ALTER TABLE`と、ターミナル3の`SELECT`が完了してプロンプトが返ってきます。

もし本番で緊急停止させたい場合は、ターミナル4にて原因となっているクエリやDDLを、
`KILL <Id>;`で強制終了させれば待機列が解消されます。

## 安全にカラムを追加するためには？
カラム追加によるテーブルロックの事故を防ぎ、安全に本番反映するための方法を2つ紹介します！

### ① マイグレーション実行時にアルゴリズム・ロックを指定する
MySQLに処理を任せきりにせず、マイグレーション実行時にオプション（`ALGORITHM` と `LOCK`）を指定する方法です。

これにより、もしも意図しないアルゴリズムが使用されそうになった場合、実行前にエラーを出すことができます。

```sql
-- INSTANTで実行されることを期待する場合
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INSTANT;

-- INSTANTが使えず、読み書きを止めないINPLACEで実行されることを期待する場合
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INPLACE,
  LOCK = NONE;
```

- `ALGORITHM = INSTANT`：メタデータの書き換えだけで終わる処理を強制する。
- `ALGORITHM = INPLACE, LOCK = NONE`：`COPY`を避け、実行中も他の読み書きを許可するよう強制する。

もし指定した条件で実行できないDDLだった場合、MySQLは処理を開始する前に `ALTER TABLE ... is not supported` とエラーを出して即座に中断してくれます。
これにより、知らず知らずのうちに、重たいテーブルロックがかかってしまう事故を未然に防止できます。

### ② ロック待ちの時間制限を設定する
先行する重たいクエリがいてロックが取れないとき、MySQLのデフォルト設定のままだと、
**最大1年間**も待ち続けてしまいます。
これは待機中クエリを増やし、サービス停止に繋がりかねません。

そこで、DDLを実行するセッションの中だけで、メタデータロックの待機上限（`lock_wait_timeout`）を短く設定しておきます。

```sql
-- この接続の間だけ、ロック待機の上限を「5秒」にする
SET lock_wait_timeout = 5;

-- カラム追加を実行
ALTER TABLE users ADD COLUMN nickname VARCHAR(255);
```

このように時間制限をつけておけば、万が一先行クエリがいてロックが取れなくても、**5秒経過した時点**で**エラーを出し処理を終了**してくれます。  
後続のクエリを延々と巻き込んでサービス全体が停止する大惨事を防ぐことができます。

## 万が一、ロックで処理が詰まってしまったときの対処法
「事前の準備はしたけれど、本番環境でマイグレーションを実行したら、サービスが止まってしまった...。」
そのような最悪のケースに直面したときの対処方法を以降にまとめていきます！

### 実行中のクエリを強制終了させる
クエリが詰まって待ちクエリが急増しているときは、一刻も早く**原因となっている処理を強制終了**して待機行列を解消する必要があります。

1. **実行中のプロセスを確認する**  
   まずはDBに入り、現在動いているクエリの一覧を表示します。
   ```sql
   SHOW FULL PROCESSLIST;
   ```
2. **原因となっているクエリを特定する**  
   注目するべきなのは `State` と `Time`（実行秒数）です。
   - `State` が `Waiting for table metadata lock` になっている `ALTER TABLE`
   - その手前で長時間 `Time` が経過したまま動いている`SELECT` や `UPDATE`
   
   待機行列の元凶となっている `ALTER TABLE`、また、それを待たせている先行クエリの ID（スレッドID）を確認します。
3. **`KILL` コマンドで強制終了する**  
   特定したIDを指定して、クエリを強制終了します。
   ```sql
   -- 例: Idが 12345 のクエリを停止する場合
   KILL 12345;
   ```
   `ALTER TABLE` を停止すれば、後ろに並んでいた `SELECT` や `INSERT` の行列が一気に流れ出し、サービスの応答が回復します。
