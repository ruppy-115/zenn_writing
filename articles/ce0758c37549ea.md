## はじめに
お疲れ様です！坪子です！

テーブルにカラムを追加する際、「テーブルロック」について事前に調べる必要がありますが、
恥ずかしながら、その理由や仕組みについてよく知らなかったため、今回調べてみることにしました。

「実際の調査ではどこを見たらいいのか」や「万が一テーブルロックで処理が詰まってしまった時の対処法」も一緒にまとめるので、是非ご覧ください！

## カラム追加の際のテーブルロックとは
データベースには、データの整合性を保つために「**ロック**」という仕組みがあります。
ロックは、同時に実行すると矛盾が起きてしまう処理同士が、互いに割り込まないよう制御しています。

MySQLにおけるロックは、内部構造に合わせておおまかに
「**InnoDBロック**」と「**メタデータロック**」の**2つ**に分かれています。

- **InnoDBロック**：テーブルに入っている「データ」を守る
  - 例：同じ行を同時に更新させない
- **メタデータロック**：テーブルの「構造（定義・設計図）」を守る
  - 例：使用中にカラムを変更させない

:::details そもそもInnoDBとメタデータとは？
**InnoDB**
MySQLの「ストレージエンジン」と呼ばれる、実際にデータを保存・管理している部分です。
MySQLは、SQLを解析・実行する「**サーバー層**」と、データを保存する「**ストレージエンジン層**」に分かれています。
※InnoDBロックはエンジン層、メタデータロックはサーバー層で管理されています。

**メタデータ**
「データについてのデータ」のことで、テーブル名・カラム名・データ型・インデックスなどの
**定義情報**を指します。

| | 例 |
|---|---|
| データ | `1, 'Runa', 'runa@example.com'` |
| メタデータ | `id BIGINT`, `name VARCHAR(255)`, `email VARCHAR(255)` |
:::

今回扱う「カラム追加時のテーブルロック」の正体は...後者の**メタデータロック**です！
テーブルの構造そのものを守るため、対象テーブル全体に対してアクセス制限（ロック）をかけます。

### メタデータロックの「共有ロック」と「排他ロック」
メタデータロックも、**2つ**に分けることができます。

- **共有ロック**  
  「テーブル定義が変わらないこと」を保証するためのロック。
  通常の`SELECT`、`INSERT`、`UPDATE`などのDMLが取得する。
  **共有ロック同士はお互いを邪魔しない**ため、同時に読み書きしても処理が詰まることはない。

- **排他ロック**  
  「テーブル定義を変更する」ためのロック。
  カラム追加（`ALTER TABLE`）などのDDLが取得する。
  **排他ロック中は他のロックを取得できない**ため、誰かがテーブルを使用している間は取得できない。

:::message
**DMLとDDLとは？**

| 種類 | 意味 | 例 |
|---|---|---|
| **DML**<br>（Data Manipulation Language） | テーブルの「データ」を操作するSQL | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| **DDL**<br>（Data Definition Language） | テーブルの「構造（定義）」を作成・変更・削除するSQL | `CREATE`、`ALTER`、`DROP` |
:::

:::details 共有ロックは同時書き込みできないのでは？と思ったそこのあなたへ
**同時書き込みができないのは、InnoDBの共有ロック**です！
InnoDBの共有ロックでは、データを守るために、書き込みを禁止します。
対してメタデータの共有ロックは、テーブル定義を守るために、定義の変更を禁止します。
そのため、データの書き込みは禁止しません。
:::

## カラム追加の際にテーブルロックについて調査する理由
ではなぜカラム追加の際に、このテーブルロックについて調査する必要があるのでしょうか。
その理由は、**たった1つのカラム追加で、サービス全体が停止する可能性があるから**です。

以降では、データベースで起きていることと、それにより引き起こされる大惨事について説明します！

### データベースの裏側で何が起きている？
トランザクション内で参照や更新を行っているテーブルに対して、途中でカラム追加が割り込んでしまうと、データの整合性が失われてしまいます。

そのためMySQLは、整合性を保つために以下のような制御を行います。

1. **先行トランザクションがメタデータロックを取得**  
   あるトランザクションがテーブルにアクセス（参照や更新など）すると、その間にテーブル定義が変わらないよう、メタデータロックを取得します。

   ![先行トランザクションがメタデータロックを取得](/images/2-1.jpg)

2. **DDLが待機状態**  
   そのトランザクションが実行されている間にカラム追加（`ALTER TABLE`）を実行すると、メタデータロックが取れずに**待機状態**になります。

   ![DDLが待機状態](/images/2-2.jpg)

3. **先行トランザクションが終了すると解放**  
   先行するトランザクションが完了（COMMIT や ROLLBACK）して、メタデータロックが解放されるまで、DDLはずっと待たされます。

   ![先行トランザクションが終了すると解放](/images/2-3.jpg)

ここまでは、データの整合性を守るための正常な処理と言えますね。
しかし、問題はこの後です...。

### 大惨事になりうる理由
「DDLが裏で待たされるだけなら、数十秒待てばいいのでは？」と、思うかもしれません。
ですが、それは危険です...！

MySQLには、「**排他ロック（DDL）が待機列の先頭にいる間、後から来た共有ロック（DML）を通してはいけない**」というルールがあります。
後続クエリを優先し続けると、DDLが永遠に実行できないためです。

その結果、**DDLが待機列の先頭**に並ぶと、**後から来た通常のクエリ（SELECTやINSERTなど）もすべてその後ろに並ばされて待機状態**になります。

![DDLが待機状態になると後続クエリも待機状態](/images/2-4.jpg)

DDLが足止めされると、ユーザーの通常アクセスも同じく足止めされるということです。
足止めだけでなく、DB接続数の上限（`Too many connections`）に達し、サービス全体が500エラーや画面フリーズでダウンしてしまう危険性もあります。

### MySQLのオンラインDDLならロックはかからない？
ここでひとつの疑問が浮かぶかもしれません。  
「**MySQLにはオンラインDDLがあるから、DDLの間も読み書きできるはずでは？**」

オンラインDDLとは、**サービスを稼働させたまま（オンラインのまま）、裏でテーブルの構造変更を行うための仕組み**です。
MySQLのバージョンアップに伴い、DDLの裏側の仕組み（アルゴリズム）は3世代に進化してきました。

#### DDLの3つのアルゴリズムと仕組み
1. **`COPY`**（MySQL 5.5以前はこれのみ）
   - **仕組み：**
   変更後の構造を持つ新しいテーブルを作成し、元テーブルの全データをコピーしてから差し替える。
   - **ロック：**
   コピー作業中は**書き込みを禁止するメタデータロック**がかかり、読み取りはできるが、**テーブルへの書き込みが遮断**される。

2. **`INPLACE`**（MySQL 5.6で登場）
   - **仕組み：**
   `COPY`のように別テーブルへデータを移さず、既存テーブルで構造変更を行う。
   作業中に発生した書き込みは一時ログに記録しておき、変更完了時にまとめて反映する。
   ※操作によっては、テーブルのデータを作り直す再構築（Rebuild）が発生する。
   - **ロック：**
   基本的には、作業中も**読み取り・書き込みの両方が可能**。

3. **`INSTANT`**（MySQL 8.0で登場）
   - **仕組み：**
   実データ（レコード）には一切手を加えず、MySQLのデータ辞書にある「テーブルのメタデータ（定義情報）」だけを書き換える。
   既存のデータはそのまま残し、読み書き時に新しい定義を適用する。
   そのため、処理時間はデータ量に依存せず、文字通り「一瞬」で完了する。
   - **ロック：**
   作業中も**読み取り・書き込みの両方が可能**。

:::details 再構築（Rebuild）とは？
**テーブルの全データを読み出し、新しい形式で1行ずつ書き直す処理**のことです。
大きなテーブルでは数十分〜数時間かかることもあります。
:::

#### オンラインDDLでも事前調査が必要な理由
「安全にDDLができそうだし、調査する必要はないのでは？」とつい考えてしまいますが、
事前調査が必須とされる理由は主に**2つ**あります！

1. **開始時に、メタデータロックを取得するから**  
  実は、`INPLACE`や`INSTANT`であっても、処理の実行には排他メタデータロックの取得が不可欠です。
  そのため、**処理の開始時にたった1つでも終了していない先行トランザクションがいれば、待機列が発生し、後続クエリを巻き込んで大渋滞**が起きます。

   ![開始時にメタデータロック](/images/2-5.jpg)

2. **すべてのカラム追加が`INSTANT`で動くわけではないから**  
  MySQL 8.0だからといって、**どんなカラム追加にも`INSTANT`が使われるわけではありません**。  
  追加する位置（MySQLのマイナーバージョンによる制限）や、データ型、制約、テーブルのオプションによっては、`INSTANT`が使えず、`INPLACE`や`COPY`が使われます。

---

「オンラインDDLがあるから大丈夫だろう」と過信せず、

- **長時間開いたままのトランザクションはないか**
- **カラム追加がどのアルゴリズム（INSTANT / INPLACE / COPY）で動くのか**

を、事前に把握しておくと安心ですね（どちらも確認方法は次章で説明します！）。

## 【ハンズオン】カラム追加が安全か調べてみよう！
理屈が分かったところで、ここからは手元のPCで実際にMySQLを動かしながら、以下を試してみましょう！

- **影響範囲を確認する**
- **長時間開いたままのトランザクションがないか確認する**
- **`ALTER TABLE`が`INSTANT`で動くか検証する**
- **【おまけ】わざとロックを発生させて、詰まる様子を見てみよう**

### 事前準備
手軽に試せるよう、Dockerを使い、MySQL 8.0の環境を用意します。

ターミナルを開き、以下のコマンドでMySQLコンテナを起動します。
```bash
docker run -d --name mysql-lock-test -e MYSQL_ROOT_PASSWORD=password -p 3306:3306 mysql:8.0
```

起動したら、MySQLに入って検証用のデータベースとテーブルを作成します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword
```

```sql
-- 検証用データベース作成
CREATE DATABASE lock_test;
USE lock_test;

-- 検証用テーブル作成
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- ダミーデータを投入（数件）
INSERT INTO users (name, email) VALUES
('Runa', 'runa@example.com'),
('Moco', 'moco@example.com'),
('Kai', 'kai@example.com');
```

これで準備完了です！

### 影響範囲の確認
まずは、対象テーブルの行数やデータサイズを調べてみましょう。
万が一、`COPY`や再構築を伴う`INPLACE`が動いた場合、**処理時間はデータ量に比例して長くなります**。

```sql
SELECT
    table_name,
    table_rows AS approx_rows,
    ROUND(data_length / 1024 / 1024, 2) AS data_size_mb,
    ROUND(index_length / 1024 / 1024, 2) AS index_size_mb
FROM
    information_schema.tables
WHERE
    table_schema = DATABASE()
    AND table_name = 'users';
```

#### 出力結果の例
```text
+------------+-------------+--------------+---------------+
| TABLE_NAME | approx_rows | data_size_mb | index_size_mb |
+------------+-------------+--------------+---------------+
| users      |           3 |         0.02 |          0.00 |
+------------+-------------+--------------+---------------+
```
本番環境で「数百万行」「数GB」規模のテーブルの場合は、処理時間が長くなるリスクが高いため、特に慎重な確認が必要です。
特に`COPY`の場合は、その間ずっと**書き込みが止まる**ので要注意です。

### 長時間開いたままのトランザクションがないかの確認
カラム追加を実行する直前に、テーブルを使ったまま終わっていないトランザクションがないか確認します。

```sql
SHOW FULL PROCESSLIST;
```

`Command`が`Sleep`なのに`Time`が長い接続は、**トランザクションを開いたまま放置されている可能性**があります。
このような接続がある時は、実行を見送りましょう。

### `ALTER TABLE`が`INSTANT`で動くかの検証
続いて、追加したいカラムが`INSTANT`で通るかを検証します。
ポイントは、**オプションを指定すること**です。

```sql
-- INSTANT を指定してカラム追加を試す
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INSTANT;
```

#### `INSTANT`で実行できた場合
```text
Query OK, 0 rows affected (0.03 sec)
Records: 0  Duplicates: 0  Warnings: 0
```
エラーにならずに成功すれば、`INSTANT`で実行されたことが確認できます。

#### `INSTANT`で実行できない場合
```sql
-- インデックス追加は INSTANT に対応していない
ALTER TABLE users ADD COLUMN age INT, ADD INDEX idx_age (age),
  ALGORITHM = INSTANT;
```
```text
ERROR 1845 (0A000): ALGORITHM=INSTANT is not supported for this operation. Try ALGORITHM=COPY/INPLACE.
```
`INSTANT`で実行できない場合、**処理を開始する前にエラーで止まります**。
`INSTANT`の代わりに使えるアルゴリズムが表示されるので、どの方法で実行されるのか事前に把握できます。

:::message alert
成功した場合は、**実際にカラムが追加されます**。
本番環境ではなく、検証環境で試しましょう。
:::

### 【おまけ】わざとロックを発生させて、詰まる様子を見てみよう
記事の前半で解説した、
「**先行トランザクションによってDDLが詰まり、後続クエリまで巻き込まれる現象**」を、
実際に手元で再現してみましょう！

ターミナルを**4つ**開いて実験します。

```text
[ターミナル1] 先行トランザクション
[ターミナル2] カラム追加
[ターミナル3] 後続のクエリ
[ターミナル4] 監視
```

#### 手順1：【ターミナル1】トランザクションを開いて放置する
まずは先行トランザクションを作り、テーブルの「共有メタデータロック」を握ったままにします。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
START TRANSACTION;
SELECT * FROM users WHERE id = 1;
-- ※ COMMIT も ROLLBACK も打たずにこのまま放置します！
```

#### 手順2：【ターミナル2】カラム追加（`ALTER TABLE`）を実行する
2つ目のターミナルを開き、カラム追加を実行してみます。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
ALTER TABLE users ADD COLUMN age INT;
```
**プロンプトが返ってこず、画面が止まります！**  
ターミナル1が共有メタデータロックを握っているため、排他メタデータロックが取れず、
DDLが待機列に並んだ状態です。

#### 手順3：【ターミナル3】後続のクエリを実行する
3つ目のターミナルを開き、ユーザーのアクセスを想定した通常の`SELECT`を実行します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
SELECT * FROM users;
```
**ただの`SELECT`ですが、画面が止まります！**  
待機列の先頭に`ALTER TABLE`がいるため、足止めされてしまいました。

#### 手順4：【ターミナル4】プロセスの状態を監視する
4つ目のターミナルを開き、何が起きているかを確認します。

```bash
docker exec -it mysql-lock-test mysql -uroot -ppassword lock_test
```
```sql
SHOW FULL PROCESSLIST;
```

##### 出力結果の例
```text
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
| Id | User | Host      | db        | Command | Time | State                           | Info                                 |
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
|  8 | root | localhost | lock_test | Sleep   |   95 |                                 | NULL                                 |
|  9 | root | localhost | lock_test | Query   |   76 | Waiting for table metadata lock | ALTER TABLE users ADD COLUMN age INT |
| 10 | root | localhost | lock_test | Query   |   21 | Waiting for table metadata lock | SELECT * FROM users                  |
| 11 | root | localhost | lock_test | Query   |    0 | init                            | SHOW FULL PROCESSLIST                |
+----+------+-----------+-----------+---------+------+---------------------------------+--------------------------------------+
```

- **Id: 9** の`ALTER TABLE`が`Waiting for table metadata lock`になっています。
- **Id: 8** は`Command: Sleep`（クエリ自体は終わっている）ですが、95秒間トランザクションを開いたまま放置しているため、これが原因だと突き止められます。

#### 手順5：【ターミナル1】のトランザクションを終了する
ターミナル1に戻って、`COMMIT;`または`ROLLBACK;`を打つと、ターミナル2の`ALTER TABLE`と、ターミナル3の`SELECT`が完了して**プロンプトが返ってきます**！

もし本番で緊急停止させたい場合は、ターミナル4にて原因となっているクエリやDDLを、
`KILL <Id>;`で強制終了させれば待機列が解消されます。

## 安全にカラムを追加するためには？
カラム追加によるテーブルロックの事故を防ぎ、安全に本番反映するための方法を2つ紹介します！

### ① マイグレーション実行時にアルゴリズム・ロックを指定する
MySQLに処理を任せきりにせず、オプション（`ALGORITHM`と`LOCK`）を指定する方法です。

ハンズオンで行った通り、もしも意図しないアルゴリズムが使用されそうになった場合、実行前にエラーを出すことができます。

```sql
-- INSTANTで実行されることを期待する場合
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INSTANT;

-- INSTANTが使えず、読み書きを止めないINPLACEで実行されることを期待する場合
ALTER TABLE users ADD COLUMN nickname VARCHAR(255),
  ALGORITHM = INPLACE,
  LOCK = NONE;
```

- `ALGORITHM = INSTANT`：メタデータの書き換えだけで終わる`INSTANT`を強制的に使用させる。
- `ALGORITHM = INPLACE, LOCK = NONE`：`COPY`を避け、実行中も他の読み書きを許可するよう強制する。

もし指定した条件で実行できないDDLだった場合、MySQLは処理を開始する前に`ALTER TABLE ... is not supported`とエラーを出して即座に中断してくれます。
知らず知らずのうちに、重たいテーブルロックがかかってしまう事故を未然に防止できます。

### ② ロック待ちの時間制限を設定する
先行する重たいクエリがいてロックが取れない時、MySQLのデフォルト設定のままだと、
**最大1年間**も待ち続けてしまいます。
これは待機中クエリを増やし、サービス停止に繋がりかねません。

そこで、DDLを実行するセッションの中だけで、メタデータロックの待機上限（`lock_wait_timeout`）を短く設定しておきます。

```sql
-- この接続の間だけ、ロック待機の上限を「5秒」にする
SET lock_wait_timeout = 5;

-- カラム追加を実行
ALTER TABLE users ADD COLUMN nickname VARCHAR(255);
```

このように時間制限をつけておけば、万が一先行クエリがいてロックが取れなくても、**5秒経過した時点**で**エラーを出し処理を終了**してくれます。  
後続のクエリを延々と巻き込んでサービス全体が停止する大惨事を防ぐことができます。

## 万が一、ロックで処理が詰まってしまった時の対処法
「事前の準備はしたけれど、本番環境でマイグレーションを実行したら、サービスが止まってしまった...。」
そのような最悪のケースに直面した際の対処方法を以降にまとめていきます！

### 実行中のクエリを強制終了させる
クエリが詰まって待機状態のクエリが急増している時は、一刻も早く**原因となっている処理を強制終了**して待機行列を解消する必要があります。

1. **実行中のプロセスを確認する**  
   まずはDBに入り、現在動いているクエリの一覧を表示します。
   ```sql
   SHOW FULL PROCESSLIST;
   ```

2. **原因となっているクエリを特定する**  
   注目するべきなのは`State`と`Time`です。
   - `State`が`Waiting for table metadata lock`になっている`ALTER TABLE`
   - その手前で長時間`Time`が経過したまま動いている`SELECT`や`UPDATE`

   待機行列の元凶となっている`ALTER TABLE`、また、それを待たせている先行クエリのID（スレッドID）を確認します。

3. **`KILL`コマンドで強制終了する**  
   特定したIDを指定して、クエリを強制終了します。
   ```sql
   -- 例: Idが 12345 のクエリを停止する場合
   KILL 12345;
   ```
   `ALTER TABLE`を停止すれば、後ろに並んでいた`SELECT`や`UPDATE`の行列が解消され、サービスの応答が回復します。
